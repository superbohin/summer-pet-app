# 版本升级与数据保护规则

这份文件是以后修改应用时的发布门槛。目标是：更新程序功能时，保留 iPad 上既有的打卡、金币、经验、爱心、兑换、任务和设置。

## 不可改变的约束

1. 生产网址必须保持不变。浏览器按“协议 + 域名 + 端口”隔离数据，更换其中任一项都不会自动读取旧网址的数据。
2. 不得删除 `summer-pet-db`，不得清空 IndexedDB 或调用 `localStorage.clear()`。
3. Service Worker 只能清理以 `summer-pet-shell-` 开头的程序缓存，不能操作用户数据库。
4. 已发布的数据字段不能直接改名或删除。必须通过迁移函数转换。
5. 数据读取或迁移失败时，不得写入默认数据；必须保留原始内容并进入保护模式。
6. 兑换和奖励必须同时写入余额与不可变交易流水，撤销也用一条反向流水表示。
7. 孩子的任务提交只进入 `submissions` 待验收队列；只有家长批准动作可以写入完成记录和奖励流水。
8. 漏喂惩罚用日期作为稳定 ID，同一天最多写入一次；升级到新规则当天开始计算，不追罚升级前日期。
9. 旧程序遇到更高数据版本时必须直接进入保护模式，不能用旧快照覆盖新数据。

## 发布一个普通功能版本

1. 修改功能代码。
2. 提升 `package.json` 的 `version`，例如从 `0.2.0` 改为 `0.2.1`。
3. `npm run build` 会自动把版本同步到 `public/version.json`、`public/sw.js` 和数据元信息，并把带哈希的 JS/CSS 注入发布版 Service Worker，保证更新后仍可离线启动。
4. 运行：

   ```bash
   npm run lint
   npm test
   ```

5. 把通过检查的同一提交部署到原生产网址。

## 改变数据结构

假设当前数据是 v3，要升级到 v4：

1. 在 `lib/game-data.ts` 中新增 v4 类型，不要直接让旧类型“假装”是新类型。
2. 新增只做单向转换的 `migrateV3ToV4`。
3. 将迁移串联为 `v1 -> v2 -> v3 -> v4`。每一步都应可重复执行，不重复发金币、重复生成兑换记录或重复扣除照料惩罚。
4. 提升 `CURRENT_SCHEMA_VERSION`。
5. 保留迁移前快照；转换完成并校验后，才能把新数据写成 current。
6. 为以下场景添加测试：

   - 完整旧数据迁移后，所有日期和打卡项目不变；
   - 金币、经验、爱心迁移前后相等；
   - 奖励与兑换流水合计能对上余额；
   - 同一份数据再次迁移不会生成重复流水；
   - 待验收任务不会提前发金币，批准一次只产生一份奖励；
   - 同一个漏喂日期重复检查不会再次扣罚；
   - 损坏数据和更高版本数据会停止写入，而不是恢复成默认值。

## 默认任务的升级

内置任务必须使用长期稳定的 ID。用户删除过的内置任务 ID 会保存在 `taskTombstones` 中，后续版本增加默认任务时不能把这些已删除任务偷偷加回来。新增默认任务应提升 `taskSeedVersion`，并只合并全新且未被 tombstone 标记的 ID。

## 发布和回退

- 发布前在应用内创建安全快照，发布后由 iPad 用户确认刷新。
- 程序可以回退，但旧程序不一定认识新版数据。发现数据版本高于程序支持版本时，应用必须进入保护模式。
- 若必须更换生产网址，先在旧网址打开应用导出 JSON，再到新网址使用“恢复备份”导入并核对流水。
- 内部快照和原数据位于同一个浏览器存储区，不能替代 iCloud/“文件”中的外部 JSON 备份。
